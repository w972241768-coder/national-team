## 这套指标能做什么、不能做什么

- **能做**：回答「谁在买、买哪个风格、相对篮子规模多大」—— 这些是事实。
- **不能做**：择时。2015-01 至 2026-11 共 2873 个交易日、按 20 交易日间隔簇化去重后，
  「滚动 95 分位托底信号」的簇起点 T+20 为 **−0.72%**、胜率 **35%**（基准 +0.25%/52%）。
  分位阈值 80/90/95/98/99 全扫，簇化后都贴着 0 或为负。
- 唯一残留倾向：沪深300 八只篮子单日净流入 > 100 亿（6~7 个独立簇，+3.61%/67%），
  簇数太少，**只能算倾向，不能算规律**，需每季度复核。

## 更新机制

- **盘中**：浏览器直连腾讯行情，每 15 秒刷新，不消耗 CI、不需要 token。
- **盘后 / 次日**：GitHub Actions 抓上交所新公布的份额，增量合并基线、重算全部统计，
  写回 `docs/data.json` 与 `docs/state.json` 并 commit（Pages 自动更新）。
- **手动**：页面右下「☁️ 重算数据」→ 粘贴一次 GitHub Token（仅存本机浏览器）→
  触发 `workflow_dispatch`；也可直接去 Actions 页点 Run workflow。

容错：任一数据源不可达时保留基线、写 warning，**绝不写坏数据覆盖线上**；
输出前做 sanity check，不合格直接让 CI 失败，Pages 继续显示上一版。
`docs/state.json` 会持久化上交所连通性探测结果（返回条数），便于不翻需要鉴权的 Actions 日志即可核对。

## 使用口径提醒（避免误读）

- **成交额放大 ≠ 一级市场申购**：ETF 成交额是二级市场买卖换手，份额增加才对应申购；
  两者不可互相推断。盘中只能看成交额异动，净流入必须等次日份额公布。
- **「>1.5 倍放量 + 午后 V 型 ⇒ 大概率有大资金申购」没有实证支撑**，本页不提供此类推断。
- **模块五的统计数字以页面实时生成为准**（数据每日重算）。历次审查中被引用但与当前数据不符的数字：
  - 「>50 亿 / >100 亿簇 T+20 = −0.66% / −0.53%」⇒ 实际 **−0.83% / −0.21%**（24 / 14 簇）
  - 「300 八只 >100 亿共 6 簇」⇒ 实际 **7 个独立簇**（19 个事件，+3.61% / 67%）
  - 「>50 亿 71 簇 / >100 亿 43 簇 / 150 亿 26 簇 +1.53%」⇒ 实际 **24 / 14 / 8 簇**，
    T+20 分别 **−0.83% / −0.21% / +1.25%**；「150 亿以上才转正」的方向正确，数字不符
  - 「2026-11-03 处于 2026-09-30 开启的放量簇」⇒ 实际簇起点为 **2026-10-09**（间隔 17 交易日）
  - 当前 `scan` 全表：`50→−0.83%(24簇)`、`80→−0.90%(13簇)`、`100→−0.21%(14簇)`、
    `150→+1.25%(8簇)`、`200→+2.76%(7簇)`、`300→+3.62%(6簇)`
- 「300 占比 >70% 权重护盘 / <50% 多风格共振」是经验解读，不是回测结论。
- **簇起点**：Top 20 表中非簇起点的行会标出所属簇起点与间隔交易日数。
  例：史上最大天量 2025-04-08（+786.5 亿）显示「簇内 · 起点 2025-04-07（+1 交易日）」，
  因为 04-07 才是那一波第一次放量。

## 页面上的两个日期 / 手机端「没数据」（2026-11-10 排查与修复）

### 11-09 与 11-10 哪个对？两个都对，含义不同

- **11-09 = 份额数据日**：上交所 T 日份额次日公布，因此能确认的最新交易日永远是上一交易日。
  KPI、日度曲线、Top20 都截至这一天。
- **11-10 = 文件生成时间**：`state.json.built_cst`，是数据文件重算完成的时刻。
- 页面顶部、口径提醒、状态条、页脚已统一标注「份额数据截至」与「文件生成时间」，并写明两者不同属正常。

### 🔴 真正让 KPI 一片 0 的 Bug（已修）

`scripts/update.py` 的 `update_nav()` 把新浪返回的带前缀 symbol（`sh510300`）直接当代码写回
`data/nav.json`，而 `build()` 用纯代码（`510300`）取价 ⇒ **价格增量全落进另一组键，计算层永远
只读到旧基线（2026-11-04）**。后果：11-05 / 11-06 / 11-09 三行 `nf / nf300 / aum / inten`
全被算成 0（指数 `idx` 仍更新，所以看起来「日期在走、数据在空」），KPI 显示 0.0 亿 / 0 亿。
上交所 403 只是「今天没抓到增量份额」的告警，**不是** KPI 归零的原因（份额基线里本来就有这三天）。

**修复**：`update_nav` 去掉 `sh/sz` 前缀并合并历史带前缀键；本地重算后
11-05 `+51.8 亿`、11-06 `+25.99 亿`、11-09 `−4.8 亿`，篮子规模 `8236.3 亿`，KPI 恢复正常。
页面另加兜底：若 `kpi.aum<=0`，在 KPI 下方明确提示「份额/价格未齐、0 不代表真实为 0」。

### 手机端「没数据」的其余原因

1. **口径硬约束**：盘中只有 26 只 ETF 的价格 / 涨跌幅 / 成交额 / 换手是实时的，当日净流入必须等 T+1。
2. **时段与时区**：页面按**北京时间**判盘中（9:15–11:30 / 13:00–15:05）；收盘后快照定格、轮询降到
   5 分钟。状态条同时给出北京时间与设备本地时间（南非 UTC+2 尤其容易误判）。
3. **第三方请求被拦**：iOS 智能防跟踪 / 微信内置 / 无痕模式可能拦 `qt.gtimg.cn`。
   页面改为 **fetch 与 `<script>` 双通道并行竞速**（不再靠 UA 猜），谁先成功用谁；两条都失败时给
   「实时源连接失败」红字 +「重试实时源」按钮，并提示换系统浏览器。
4. **分时曲线空**：腾讯 `web.ifzq.gtimg.cn` 偶发整体 501（服务端），与手机无关；
   页面保留上次曲线并 5 分钟自动重试。

### 🔴 再次复盘：手机「整页空白」的真正原因（2026-11-10 第二次修复）

上一轮用桌面浏览器 + iPhone UA 模拟能通过，真机仍空白，差异在**网络而非设备**：
`data.json` 约 343 KB，旧启动逻辑把 `render(D)` 放在该请求成功之后，
**一旦手机弱网 / 内置浏览器让它超时或被拦，所有区块都停在「载入中…」**，
连错误提示都在屏幕下方，看起来就是整页没有数据。

**修复（结论前置 + 离线兜底）**：

1. `scripts/verdict.py` 在数据重算时，把完整结论卡 HTML 与 26 只行情代码表
   （共约 6 KB）**写死进 `docs/index.html`**；`payload["verdict"]` 同步进 `data.json`
   （CI 每日提交，在线结论自动更新）并缓存进浏览器 `localStorage`（离线快照保鲜）。
2. 启动顺序改为「结论 → 明细（10 秒超时，可失败）→ 实时行情（不依赖明细）→ 状态文件」；
   明细失败时只降级明细区并给「重新加载明细」按钮，结论与实时行情照常。
3. `data.json` 失败时用内嵌代码表跑腾讯行情 / 分时，`fetch` 与 `<script>` 双通道继续竞速。
4. 冗长的口径说明与状态条收进默认折叠的「⚙️ 数据说明」抽屉；新增「🔍 自检」按钮。

**验收**（390×844 / iPhone UA）：结论卡距页顶 146 px；
拦截 `data.json` 时四个数字完整、26 只行情 0 只不可用；
**完全禁用 JavaScript** 时结论卡与四个数字依然完整显示。

状态条仍在抽屉内（两个日期含义 / 已确认值 / 数据源 / 时区 / 通道 / 五条提醒），需要时点开即可。
